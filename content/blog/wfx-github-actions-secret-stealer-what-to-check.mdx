Last week a campaign started pushing a credential stealer into GitHub repositories using nothing but stolen tokens. No GitHub vulnerability, no zero-day, no clever exploit chain. Just valid credentials, write access, and a CI system that does what it is told.

[Aikido](https://www.aikido.dev/blog/compromised-github-accounts-push-ci-secret-stealer-to-tens-of-thousands-of-repositories) and [StepSecurity](https://www.stepsecurity.io/blog/wfx-phantom-the-github-actions-secret-stealer) both published write-ups on 12 November. This post is the part I care about: how it works, how to find out whether you were touched, and what to clean up. The cleanup is not just "rotate your secrets".

## What happened

According to Aikido, the campaign began around 12:45 UTC on 10 November. An actor holding stolen GitHub tokens from [4,837 accounts](https://www.aikido.dev/blog/compromised-github-accounts-push-ci-secret-stealer-to-tens-of-thousands-of-repositories) opened probe pull requests in 61,764 repositories to find out where those tokens had write access. The stealer then ran in at least 1,806 of them. Aikido's own page also says 1,835 in its summary, so treat all of these as lower bounds from one vendor's data.

StepSecurity is explicit that the attacker ["does not exploit a bug in GitHub Actions"](https://www.stepsecurity.io/blog/wfx-phantom-the-github-actions-secret-stealer). They also say they have not established how the tokens were obtained. Some of the tokens were issued to the Fly.io GitHub app, but StepSecurity says it has no evidence of a breach of Fly.io's own infrastructure.

The [Cloud Security Alliance briefing](https://labs.cloudsecurityalliance.org/research/alt-ciso-briefing-2026-11-12/) described the campaign as still active as of 12 November, so assume the details below will keep shifting.

## How the attack works

Per both write-ups, the attacker does three things in each repository a token can write to.

**1. Probe.** Open a pull request titled `docs: dependency audit notes` from a branch named `wfx-docs`. It does nothing on its own. It proves the token can write.

**2. Payload.** Push a roughly 1,500-line shell script in one of several ways:

- Edit an existing workflow so one step passes `toJSON(secrets)` to the next, committed as `ci: refresh build cache`.
- Add a new workflow file named `build-audit-` plus six characters on a throwaway `chore/` branch.
- Add a hidden `.ci-` script and wire it into `package.json` as a `postinstall` hook, committed as `chore: add ci helper`.

**3. Cleanup.** Revert the commit and delete the workflow run and its logs, usually within a minute. Aikido says a missing run number in the workflow's history is often the only trace.

That last point is the detection hint worth remembering. Run numbers are sequential. A gap means something ran and was deleted.

## What the script takes

The stealer collects Actions secrets and variables, the `GITHUB_TOKEN`, cloud credential files, AI provider keys, and, according to StepSecurity, the memory of the `Runner.Worker` process, which holds decrypted secrets including ones the workflow never asked for.

Then it escalates. It uses the job's OIDC token to open AWS, GCP and Azure sessions. This is the part I'd want every platform team to absorb: OIDC federation removed the long-lived cloud key from your repo, but a workflow that can run attacker-chosen code can still ask for a session.

## Why rotation is not enough

This is the finding that changes your response. Both vendors describe persistence that survives rotating every secret:

- **AWS:** the script rewrites an assumed role's trust policy to `"Principal": {"AWS": "*"}`, which lets any AWS account assume it, and tries `iam:CreateAccessKey` for long-lived keys.
- **Azure:** it adds federated identity credentials named `wfx-ci-` plus a number to app registrations. Aikido's description: any workflow in that repository can then authenticate to Azure without a stored secret, even after every token has been rotated.
- **Branch protection:** Aikido says it can post forged `success` commit statuses using your required check names, because protection matches on the context name rather than on who posted it. StepSecurity reports that none of the 101 copies it examined had this turned on, but the capability is there.

So the order is: find out if it ran, remove the persistence, then rotate.

## How to check your own org

Start with GitHub. The probe is the easiest signal:

```bash
# Probe PRs across an org (needs the GitHub CLI)
gh search prs --owner YOUR_ORG "docs: dependency audit notes" \
  --json repository,author,url,createdAt

# Leftover branches from the campaign
gh api "repos/YOUR_ORG/YOUR_REPO/branches" --paginate --jq '.[].name' \
  | grep -E '^(wfx-docs|chore/[a-z0-9]{8}|ci-check-[0-9]{4})$'
```

Then look for run-number gaps on repos where a commit with one of the published messages landed after 10 November. A probe PR is evidence that a token was compromised, even where the payload never ran. The account that opened it is the one to lock down.

Then the cloud side. These are the checks I'd run:

```bash
# AWS: roles whose trust policy allows any principal
aws iam list-roles \
  --query "Roles[?AssumeRolePolicyDocument.Statement[?Principal.AWS=='*']].RoleName"

# AWS: access keys created since the campaign started
aws iam list-users --query 'Users[].UserName' --output text | tr '\t' '\n' \
  | xargs -I{} aws iam list-access-keys --user-name {} \
      --query "AccessKeyMetadata[?CreateDate>='2026-11-10'].[UserName,AccessKeyId]"
```

For Azure, list the federated credentials on each app registration and look for names starting with `wfx-ci-`. For AWS CloudTrail, StepSecurity suggests looking for role sessions named `wfx-` followed by `CreateAccessKey` or `UpdateAssumeRolePolicy`. For GCP, review `GenerateAccessToken` and `SignJwt` calls made through your GitHub workload identity pool.

The vendors publish [hashes and IPs](https://www.stepsecurity.io/blog/wfx-phantom-the-github-actions-secret-stealer), but StepSecurity warns that file hashes are of limited use because every copy embeds its target repo and random names. Their exfiltration also moved from raw IPs to Telegram within two days, so a blocklist built on 10 November misses later copies. Search your egress logs for the IPs and for `api.telegram.org` from runners, but do not treat a clean result as clean.

## What to do if it ran

My order of operations:

1. **Lock the account.** Revoke the personal access tokens, OAuth grants and SSH keys of whoever pushed the commit, and sign out their sessions.
2. **Remove persistence first.** Delete wildcard trust policies, delete access keys created since 10 November, delete `wfx-ci-` federated credentials.
3. **Rotate everything the job could reach.** Repo, environment and org secrets, registry publish tokens, and any cloud keys. Assume the stealer saw all of it.
4. **Check what you published.** If a package was built between the malicious commit and the revert, rebuild it from a clean commit. A revert removes code from the branch, not from history.
5. **Developer machines.** The `postinstall` variant runs on any `npm install`, so anyone who installed in that window should rotate their own credentials.

StepSecurity says GhostAction victims from October who left secrets unrotated were [hit again](https://labs.cloudsecurityalliance.org/research/alt-ciso-briefing-2026-11-12/). Incomplete cleanup gets you compromised twice.

## What I'd change before the next one

None of this needs new products. It needs the settings you already have:

- **Treat bot accounts like maintainers.** StepSecurity found the attacker pushing as a project bot that could bypass branch protection. A token with write access and bypass rights is a maintainer account that never sleeps.
- **Do not let default-branch workflow edits run unreviewed.** The injected workflow change went straight to the default branch, so it ran without a pull request review.
- **Scope OIDC trust tightly.** In AWS, Azure and GCP, bind the trust to a specific repository, branch or environment, not just to "GitHub". Put cloud-deploying jobs behind a protected environment with required reviewers, so a stolen write token cannot reach the role alone.
- **Use an egress allowlist on runners.** A bare IP or `api.telegram.org` does not belong in a normal build. StepSecurity makes the same point.
- **Alert on `toJSON(secrets)`.** I can't think of many legitimate reasons for a build to serialize every secret at once.
- **Use fine-grained tokens with short lifetimes.** The less a stolen token can write to, the smaller the probe's hit rate.

## What I would not over-read

The numbers come from two vendors who sell detection products, and they disagree slightly with each other. How the tokens were stolen is still unknown. The campaign is ongoing, and the stealer's behaviour has already changed once. I would plan around the mechanism, which is stable, rather than the indicators, which are not.

The mechanism is the lesson. A developer's GitHub token is a key to every cloud account and AI service that developer's repositories trust. Look at your org with that in mind today.
