On 11 November the Apache HTTP Server project [released 2.4.71](https://httpd.apache.org/security/vulnerabilities_24.html), which fixes three CVEs. One of them is the kind you stop your afternoon for: CVE-2026-119618, a critical bug in `mod_http2` that Apache describes as a "Concurrent Execution using Shared Resource with Improper Synchronization vulnerability in Apache HTTP Server's mod_http2 in assign_headers() can lead to RCE".

Unauthenticated remote code execution in the HTTP/2 handler of the web server a large share of the internet runs. Red Hat [rates it 9.8](https://access.redhat.com/security/cve/CVE-2026-119618) with the vector `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` and assesses it as Critical. There is no NVD or cve.org score on that page yet.

This post is the triage I'd run: who is actually exposed, how to check it rather than guess, and what to do today.

## What is affected

Per the [Apache advisory](https://httpd.apache.org/security/vulnerabilities_24.html):

- Apache HTTP Server from **2.4.55 through 2.4.70**.
- The standalone `mod_h2` module from GitHub, from **2.0.8 through 2.0.42**.
- Fixed in **2.4.71**, released 11 November 2026.

The important qualifier is configuration. Red Hat's statement is blunt about it: "Only servers that have HTTP/2 enabled are affected; servers configured to serve only HTTP/1.1 are not vulnerable." The trigger is `h2` or `h2c` appearing in your `Protocols` directive.

That qualifier is why I'd treat the headline exposure numbers as an upper bound. Wiz [reports](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability) that "64% of cloud environments have resources vulnerable to CVE-2026-119618" and that 51% have publicly exposed instances, but adds the caveat directly: "Note that this does not take configuration into account." Those are version counts, not exploitable-host counts. Yours could be lower. It could also be most of your fleet, because HTTP/2 is just how servers are set up now. The point is that you can check this in a minute instead of arguing about it.

## The bug, in one paragraph

HTTP/2 multiplexes many requests over a single connection. Apache services those streams with worker threads while connection-level state belongs to the connection thread. Red Hat's description of the root cause is the clearest I've read: "a worker thread writes into memory owned by the connection thread through a shared, lock-free allocator". One thread modifies memory another thread owns, the heap gets corrupted, and from there you are in classic memory-corruption territory.

The [fix commit](https://github.com/apache/httpd/commit/824beab9b9424d6cfb29595248fdbf6c3dddeab1) is a single changed line in `modules/http2/h2_request.c`. The code that signals a zero content length now writes `Content-Length: 0` into the request record's own `headers_in` table instead of the header table hanging off the shared `h2_request`. No new mutex, no reordering, no bounds check. One token, CVSS 9.8.

I find that worth sitting with. The bug is not exotic cryptography or a parser edge case. It is writing to the wrong table from the wrong thread, in code that has shipped since 2.4.55.

It also explains why severity varies by build. Red Hat rates RHEL 9 and RHEL 10 as Important rather than Critical because their `mod_http2` packages "allocate each HTTP/2 stream from a separate allocator, which substantially increases the complexity of exploiting the flaw". Same CVE, different exploitability, depending on whose binary you run.

## Is it being exploited?

The sources disagree, and that disagreement is itself useful:

- Wiz, on 11 November: "As of the time of this blog's publication, no exploit is available and there are no reports of exploitation in the wild."
- Red Hat's statement: "public research has demonstrated a reliable exploit against a default-configured server with the mod_http2 module enabled". The advisory does not name the research.
- SecurityWeek [notes](https://www.securityweek.com/apache-patches-critical-http-server-rce-found-by-anthropic-google/) that a public proof of concept reproduces memory corruption and Apache process crashes, but does not demonstrate remote code execution.

So: a public PoC that crashes the server, and a vendor saying reliable exploitation has been demonstrated somewhere. I'd plan as if a working exploit exists. Memory corruption that reliably crashes a process is the hard part; weaponising it is a matter of someone deciding to.

## How to check your own servers

Start with the module and the protocol, not the version string.

```bash
# Is mod_http2 even loaded?
apachectl -M 2>/dev/null | grep -i http2

# Is h2 or h2c actually enabled?
grep -ril --include='*.conf' -e 'Protocols' /etc/httpd /etc/apache2 2>/dev/null \
  | xargs grep -i 'Protocols'

# What version does the binary think it is?
apachectl -v
```

Then confirm from the outside, which is what an attacker sees:

```bash
# TLS: does the server negotiate h2 over ALPN?
curl -sI --http2 https://your-host/ | head -1

# Cleartext h2c, which people forget is also in scope
curl -sI --http2-prior-knowledge http://your-host/ | head -1
```

Two traps I'd watch for.

**The upstream version number lies on distributions.** Debian, Red Hat and friends backport fixes without bumping the upstream version, and on Red Hat systems the affected code ships as `mod_http2` with its own package version, [tracked separately from httpd](https://access.redhat.com/security/cve/CVE-2026-119618). Compare against your distribution's security tracker, not against 2.4.71.

**Containers do not patch themselves.** If `httpd` runs in an image, a host-level `apt upgrade` changes nothing. You need a rebuilt base image and a redeploy, and you need to find every image in your registries that includes it. Wiz makes the related point that a compromised Apache instance inside a cluster is a foothold for reaching adjacent microservices or cloud metadata endpoints, which is exactly why an internal-only Apache is not automatically a non-issue.

## What to do

1. **Patch to 2.4.71 or your vendor's package.** The Apache advisory lists no workaround for this CVE.
2. **If you genuinely cannot patch today, turn HTTP/2 off.** Setting `Protocols http/1.1` removes the attack surface, which both Wiz and Red Hat's scoping statement support. You lose multiplexing, so treat it as a holdover, not a fix.
3. **Check where HTTP/2 is terminated.** If a CDN or load balancer speaks h2 to clients and HTTP/1.1 to your origin, the origin is not reachable by this bug — but the edge still needs looking at if it is also Apache. This follows from the HTTP/2-only scoping, so verify your own topology rather than taking my word for it.
4. **Patch the other two while you are there.** 2.4.71 also fixes CVE-2026-106023, an important NULL pointer dereference in `mod_md` that crashes child processes, and CVE-2026-109163, a low-severity one-byte stack overwrite in `mod_vhost_alias` affecting 2.4.69 and 2.4.70.
5. **Look back through your error logs.** The public PoC crashes worker processes, so segmentation faults in `error_log` and unexplained child exits are the cheapest signal you have that someone has been poking at this.

## One thing I keep thinking about

This bug was found twice, independently, within nine days. Apache credits "Anthropic's OSS Scanner" for a report on 26 October, and Anthony Weems and Simon Scannell of Google Cloud Vulnerability Research for an independent report on 3 November.

Whatever you think about automated vulnerability discovery, the throughput is changing. The same Apache page shows 2.4.69 shipped with 20 CVEs in October 2026, against 5 in the December 2025 release. If old, widely deployed C code is now being swept continuously, the practical consequence for the rest of us is that web server patching stops being an occasional event and becomes a normal part of the release cadence. Plan the pipeline for that, not for one emergency.
